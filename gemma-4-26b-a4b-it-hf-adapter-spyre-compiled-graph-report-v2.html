Layer structure: what are _compiled_prefill_attn and _compiled_prefill_ffn?

Gemma-4-26B uses a MoE decoder (Mixture-of-Experts). Every decoder layer is implemented as a Gemma4MoEBlock in hf_gemma4_moe.py. The HF adapter manually splits each block into two separately compiled sub-graphs to keep compilation units manageable and to isolate the attention KV-cache mutation from the FFN computation:

_compiled_prefill_attn (graph 2 in this trace) wraps _attn_forward. It covers the entire attention sub-layer of one decoder block: input RMSNorm → Q/K/V projections (via BMM) → per-head RMSNorm on q/k/v → RoPE (matmul-based) → KV cache scatter-write (index_put + copy_) → GQA expansion (8 KV heads → 16 Q heads) → scaled-dot-product attention decomposed into online softmax + BMMs → output projection → post-attention RMSNorm → residual add. It receives the full set of attention weight tensors as inputs and the two KV cache buffers as mutable side-effect tensors.

_compiled_prefill_ffn (graph 3 in this trace) wraps _prefill_ffn. It covers the entire FFN sub-layer: input RMSNorm → dense MLP path (gate/up/down projections via BMM + GeLU) running in parallel with the MoE path — router softmax → top-8-of-128 expert selection (spyre.topkindex) → routing weight computation → all-experts batched BMM (gate/up/down, shape [128,64,704]) → weighted sum across experts (sum(dim=0)) → post-FFN RMSNorm → residual add → layer scalar multiply.

Why graphs 2 and 3 are representative of all 62 decoder layers

Gemma-4-26B has 62 decoder layers. Every layer has the same Gemma4MoEBlock structure — the same two compiled regions with the same op graph, just different weight tensor values. The adapter compiles each region with torch.compile at the class method level (not per-instance), so after the first layer compiles and populates the cache, all subsequent layers reuse the same compiled artifact. The trace shows graphs 0–3 because only the first layer triggers compilation; later layers hit the cache. This means graphs 2 and 3 fully describe the op-level computation for every decoder layer in the model.

The two exceptions are layers that use global (non-sliding) attention — those differ in KV cache size and mask shape but the op types are identical. The dense-vs-MoE layer split is uniform across all 62 layers in this model variant.

What is missing

The trace covers one complete decoder layer (graphs 0–3). What is not captured due to the crash:

  • The second layer's _compiled_prefill_ffn — compilation aborted before it finished. In practice this is the same graph as graph 3.
  • The final language model head (lm_head linear projection) and any post-backbone normalisation — these would be separate compiled regions not reached.
  • Token-generation (decode) graphs — the adapter uses different compiled paths for single-token decode steps; those are not shown here at all.

The crash: expected exactly 1 reduction variable, got set()

Where: torch_spyre/_inductor/wsr/propagate_named_dims.py → find_reduction_var, called from _compute_named_dims during the pre-scheduling pass for the second layer's _compiled_prefill_ffn.

Full traceback root: aten.sum.dim_IntList(mul_12, [0]) — the MoE expert-weighted sum that reduces over dim 0 (the expert dimension, size 128) to produce bf16[64, 2816].

The Spyre named-dims pass assigns symbolic named dimensions to every loop variable in every scheduled buffer so the compiler can reason about tiling and work distribution. For a reduction op it needs to find exactly one reduction variable — the loop variable that iterates over the reduced axis — to annotate it as a reduction dim.

In this case the reduction is over dim 0, size 128 (the expert axis of bf16[128, 64, 2816]). The named-dims propagation pass could not find a named-dim mapping for that loop variable — it returned an empty set instead of exactly one symbol. This happens because the expert dimension (128) was not given a named dim label by any upstream op in the graph, so the propagation chain has no name to attach to it when the reduction node is visited.

The crash is deterministic: it fires on the second layer because the first layer's FFN was compiled before the named-dims pass was improved to handle this shape, but on the second run the cache is not hit and the pass runs again. In practice, graph 3 from the first layer and the would-be graph from the second layer are identical in structure, so this crash blocks no new information — it is a known limitation tracked against the named-dims pass for multi-dim reductions on the expert axis.
