Tensor Layout Propagation: View on Pointwise / Reduction

How SpyreTensorLayout (the stick dimension) is computed in _single_arg_op_layout() when a view sits on top of an op.

Background: What is a SpyreTensorLayout?

Spyre hardware stores tensors in a tiled stick layout. The innermost device dimension — called the stick — holds a fixed number of elements in a contiguous hardware register: 64 elements for fp16, 32 elements for fp32. Every other dimension forms outer tiles over those sticks.

SpyreTensorLayout fields
device_size — concrete size of each device dimension
stride_map — stride of each device dimension in elements
dim_order — permutation placing the stick dimension last
dtype — device dtype (governs stick width)

The stick dimension is always the last in dim_order. Changing which logical tensor dimension becomes the stick is the entire subject of layout propagation.

The Op Graph Structure

Inductor fuses a view (reshape/squeeze/unsqueeze/slice) into the same ComputedBuffer as the following op. The fused node's MemoryDep carries the view's index expression, so a view is invisible as a separate node — it lives in the index formula of the read dependency.

View + Pointwise

input [4, 4, 16] fp16
↓
fused view index
↓
ComputedBuffer (Pointwise)
relu(view(x, [16,16]))
output [16, 16]

View + Reduction

input [4, 4, 64] fp16
↓
fused view index
↓
ComputedBuffer (Reduction)
sum(view(x,[16,64]), dim=1)
output [16]

Layout propagation calls _single_arg_op_layout(op, output, output_dep, dep, in_layout, stl) where dep is the read MemoryDep (whose .index encodes the view) and stl is the candidate SpyreTensorLayout for the input.

Step 0: Computing Coordinates

Two coordinate systems are computed by compute_coordinates() in views.py:

FunctionInput to the algorithmOutput
host_coordinates(layout, dep) Host FixedLayout strides + dep index Per-dimension symbolic expressions in the host (logical) space
device_coordinates(stl, dep) Device SpyreTensorLayout strides + dep index Per-device-dimension expressions; last entry is the stick expression

The view's index expression (e.g. ModularIndexing terms from a reshape) is already baked into dep.index. Both coordinate functions decode that expression against the respective stride arrays to recover per-dimension terms.

Path A — View on top of Pointwise

Entry point: the isinstance(data, Pointwise) branch in _single_arg_op_layout() (lines 264–346 of propagate_layouts.py).

Fast path (no layout change needed)

1
Compute in_coords = host_coordinates(in_layout, dep) and out_coords = host_coordinates(output, output_dep).
2
If all four conditions hold: 
in_coords == out_coords          # same per-dim access pattern
in_layout.size == output.size    # same shape
dep.index == output_dep.index    # same flat index
same_device_size(in dtype, out dtype)  # no elem-size change
then the tensors are accessed identically. The device layout is propagated unchanged — only the dtype field is updated.
This fires for an elementwise op with no reshape, e.g. relu(x).

View path (shape changes)

When the fast path fails (a reshape has changed the shape), the algorithm works in device coordinate space:

3
Compute in_device_coords = device_coordinates(stl, dep). Extract the input stick expression: stick_expr = in_device_coords[-1].
This is a symbolic expression like Mod(d2, 64) saying "element position inside the stick is the loop variable d2 modulo 64".
4
Call _output_stl_from_stick_expr(stick_expr, output, output_dep, …).
This checks two things:
  • Offset-free? — is_stick_expr_offset_free(stick_expr, 64) must be true. A slice that starts mid-stick would produce Mod(d2,64) + 3, which fails here.
  • Survives reshape? — matching_dim(out_coords, stick_expr) finds which output dimension the stick expression maps to. If no unique output dim carries this expression, the stick dimension was destroyed by the reshape.
If both pass, that output dimension is made the new stick and the result is returned immediately.
5
Fallback — if step 4 returned None (stick lost in reshape, or had offset), call _candidate_output_stls() which scans every non-last output dimension as a candidate stick. Only dimensions whose resulting device stick expression is offset-free are kept. Multiple candidates can survive — each becomes one entry in op.layouts.

Concrete example: relu(x.view(16, 16)), input [4, 4, 16] fp16

Input STL: stick on dim 2 (size 16, fits in 64-elem stick with 48 padding elements)

dim 0
size=4, stride=64
dim 1
size=4, stride=64
dim 2 ★
×16
+48 pad
size=64 (device), stride=1

After view([16,16]):

dep.index = d0 * 16 + d1 (flattened from d0*64 + d1*16 + d2). out_coords = [d0, d1]. Input stick expr = Mod(d2, 64) which involves d2, but the output has no d2 — stick dimension is merged into dim 1. matching_dim fails → fallback scans dim 0 of the output. dim 0 has size 16, which is divisible by 64? No. dim 1 has size 16, same issue. So the candidate stick becomes the last dim of the output with appropriate padding.

Output STL: stick on output dim 1, device size [16, 64] (size 16 padded to 64-elem stick).

Path B — View on top of Reduction

Entry point: the isinstance(data, Reduction) branch in _single_arg_op_layout() (lines 226–262).

The key difference from pointwise: a reduction collapses one or more input dimensions entirely. The collapsed dimension disappears from the output, so the stick may have to migrate.

1
Compute x_dev_coords = device_coordinates(stl, dep) and out_coords = host_coordinates(output, output_dep). Extract x_stick_expr = x_dev_coords[-1].
2
Attempt to preserve input layout — same _output_stl_from_stick_expr(x_stick_expr, …) call as pointwise. If the stick dimension survives the reduction (i.e. it is not the reduced dim) and maps to a unique output dim, this returns immediately.
3
Fallback scan over input dimensions. Identify the reduction variable: 
reduction_var = dep.index.free_symbols − output_dep.index.free_symbols
This is the loop variable that disappears into the output (e.g. r0). Then for each input dimension in_dim:
  • Skip if size[in_dim] % 64 ≠ 0 (no valid stick alignment).
  • If in_coord[in_dim] carries the reduction variable → this dim is collapsed, so out_stick_dim = −1 (innermost output dim becomes the stick).
  • Otherwise → map to an output dim via matching_dim(out_coords, in_coord[in_dim]). If it maps, that output dim is the candidate stick.
Each surviving candidate produces one SpyreTensorLayout added to op.layouts.

Concrete example: x.view(16, 64).sum(dim=1), input [4, 4, 64] fp16

Input STL: stick on dim 2 (size 64, exact fit — no padding)

dim 0
size=4
dim 1
size=4
dim 2 ★
×64 (reduced)
size=64, stride=1

After view([16,64]): the reduction_var = r0 (ranges over 64). Input stick expr = Mod(r0, 64). It carries r0.
_output_stl_from_stick_expr computes out_coords for output [16] — the output has no symbol matching r0, so matching_dim returns None. First attempt fails.

Fallback scan: dim 1 of the input (size 64 ✓) carries r0 → out_stick_dim = −1 → output STL gets stick on the single output dim (dim 0, size 16).

Output STL: device_size=[64] (16 padded to 64-elem stick), stick on dim 0.

What happens when the stick survives the reduction

Example: x.sum(dim=0) on [8, 64] where stick is on dim 1 (the non-reduced dim).
x_stick_expr = Mod(d1, 64). d1 is not the reduction var. _output_stl_from_stick_expr finds output dim 0 carries d1. Layout preserved: output STL has stick on dim 0, same device stride.

The Critical Constraint: Offset-Free Sticks

Both paths gate every candidate on is_stick_expr_offset_free(expr, elems_per_stick). A stick expression must be one of:

FormExampleMeaning
Mod(var, N)Mod(d2, 64)Standard tiled stick
var (bare symbol)d2Dim smaller than stick width
00Scalar / broadcast

A slice that starts mid-stick produces Mod(d2, 64) + 3. This fails the check and that candidate is discarded. If all candidates are discarded, _single_arg_op_layout returns an empty list, and compute_layouts raises Unsupported.

Decision Summary

Scenario Fast path? Stick outcome Code path
Pointwise, no shape change Yes Propagated unchanged lines 324–335
Pointwise view, stick dim survives reshape No Mapped to corresponding output dim _output_stl_from_stick_expr
Pointwise view, stick dim merged/removed No Scan all output dims; pick first offset-free _candidate_output_stls
Reduction, stick on non-reduced dim No Stick maps to surviving output dim _output_stl_from_stick_expr
Reduction, stick on the reduced dim No Dim collapses → stick on innermost output dim Fallback scan, out_stick_dim = −1
View starts mid-stick (slice with offset) No Candidate discarded → Unsupported is_stick_expr_offset_free gate

How to Observe This at Runtime

TORCH_LOGS="spyre.inductor.propagate_layouts:DEBUG" \
TORCH_COMPILE_DEBUG=1 \
python your_script.py 2>&1 | grep -E "stick|STL|layout|Mod"

The logger is named spyre.inductor.propagate_layouts (created via get_inductor_logger("propagate_layouts") at line 80 of propagate_layouts.py). The existing debug block at line 762 prints device coordinates with indirect-index substitutions. For direct inspection of the view paths you can temporarily add logger.debug(f"stick_expr={stick_expr}, out_stl={out_stl}") just before the return sites at lines 335 and 345.
