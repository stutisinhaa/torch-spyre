Gemma 4 26B-A4B-it — View Operations on torch-spyre

Compiled-path (torch.compile) view op support analysis · 46 transformer layers · MoE FFN · GQA (28 Q heads / 14 KV heads) · head_dim=256 · hidden=3584

Where View Ops Appear in the Model

Attention (every layer)
QKV projection output [B, S, H*D] → reshape/view → [B, S, H, D] → permute(0,2,1,3) → [B, H, S, D] → bmm.
GQA head replication: K/V[B,14,S,256] → unsqueeze(2) → expand(-1,-1,2,-1,-1) → flatten(1,2) → [B,28,S,256].
After SDPA: [B,H,S,D] → transpose(1,2) → clone(contiguous_format) → output projection.
MoE Routing & Dispatch (every other layer)
Router logits → softmax → top-k selection.
Token dispatch: select/narrow to slice token subsets per expert → expert matmul → cat to merge outputs back.
Expert weight matrix: static split across experts (dim=0).
Linear (nn.Linear, every projection)
3D input [B, S, H] → view([B*S, H]) → mm → view([B, S, H_out]).
Eliminated by Spyre's mm_to_bmm_pass; replaced with bmm on 3D inputs, so these reshapes disappear from the compiled graph.
RoPE positional embeddings
Frequency tensor construction uses unsqueeze + expand for broadcasting.
Query/key split into halves: split or narrow along head_dim → rotate → cat to recombine.
KV Cache (inference)
Cache update: cat past and current K/V along sequence dimension.
Shapes: [B, 14, past_len+S, 256]. Stick boundary at past_len — only safe if past_len is a multiple of 64 (fp16 stick size).

Key Risks for Gemma 4 on torch-spyre

🔴
KV Cache cat boundary alignment
cat along the sequence dimension requires the existing cache length (past_seq_len) to be a multiple of 64 (fp16) or 32 (fp32). Dynamic prefill lengths break this. Mitigation: pad to stick boundaries or use static shapes only. File: lowering.py:962, customops.py spyre::slice.
🔴
MoE dynamic token dispatch — select/narrow with symbolic shapes
MoE routing assigns different numbers of tokens to each expert — the count is data-dependent, not statically known. Dynamo with torch.compile requires static shapes. This is the primary blocker for MoE inference. Workaround: torch.compile(..., dynamic=False) with fixed batch/sequence sizes, or mark token count as static.
🔴
reshape — incompatible layout falls to spyre::reshape_via_cpu
When a reshape is not representable as a zero-copy strided view (e.g., reshaping across stick-straddling dims), it silently routes to spyre::reshape_via_cpu (customops.py:453) — a full CPU round-trip. In a 46-layer model this can cause significant latency and graph breaks. Identify all non-contiguous reshapes in the traced graph before benchmarking.
⚠️
permute → restickify per attention layer (performance)
Every permute(0,2,1,3) in attention (3–4× per layer × 46 layers = ~138–184 restickify nodes) injects a full data copy. permute_fusion is disabled in patches.py. This is expected behavior but is a significant performance overhead. Benchmark against CPU/GPU to quantify.
⚠️
expand (stride-0) materialization for GQA
GQA head replication via unsqueeze+expand+flatten always materializes the expanded tensor before bmm (one copy per layer pair). Handled correctly in decompositions.py:562 but adds memory and compute overhead proportional to num_kv_heads × expansion_factor × S × head_dim.
⚠️
RoPE split at head_dim//2 — safe only if ≥64 alignment
Gemma 4's head_dim=256, so split at 128 is stick-aligned (128 mod 64 = 0). This is safe. However, if a variant uses head_dim=128 (split at 64) or head_dim=64 (split at 32), the second half would not be stick-aligned for fp16 → potential restickify or layout error.
✅
Shapes are generally stick-aligned for the 26B-A4B config
hidden_size=3584 (3584 mod 64 = 0), head_dim=256 (256 mod 64 = 0), num_heads=28, num_kv_heads=14. All key dimensions are multiples of 64. This means most view operations will be zero-copy or safely restickified without correctness issues — assuming fixed sequence lengths.
