View Operations & Restickification on Spyre

A reference covering when a PyTorch view operation leads to a restickify on the Spyre device backend, why it happens, and which source files determine it.

Background: Sticks, Stickify, and Restickify

Spyre stores tensor data in sticks — 128-byte-aligned chunks. Float16 packs 64 elements per stick; float32 packs 32 elements per stick. When a tensor first arrives on the device it is stickified: rearranged into this tiled layout described by a SpyreTensorLayout (with fields device_size, stride_map, and device_dtype).

A restickify is a device-side data-movement operation that converts a tensor from one stick layout to a different one. It costs real memory bandwidth and is inserted by the compiler when a layout mismatch is detected on an input edge.

Free (metadata only) View ops copy the existing SpyreTensorLayout unchanged — no device data moves.   Restickify triggered happens when the next op has a hardware constraint on which dimension must be the stick dimension and the inherited layout doesn't satisfy it.

The view itself never touches device data. The restickify is inserted after the view, before the consuming op, when finalize_layouts() walks every input edge and finds the committed layout is incompatible with what the op requires.

The Five Scenarios
1
View changes which dimension is the stick, and the next op is a matmul
Consumer: mm / bmm

The hardware rule

Matmul (DF16) requires: x (left input) stick on the K (reduction) dimension; y (right input / weight) stick on the N (output-column) dimension.

Why a view causes it

A view() or reshape() is free — it just updates host-side size/stride metadata and copies the old SpyreTensorLayout unchanged onto the new tensor. But if the shape change causes the dimension that used to be "K" to no longer map cleanly to the stick in the inherited layout, the matmul sees an incompatible input. find_stick_compatible_input_layout() has two passes: first it checks whether any existing candidate layout already satisfies the stick requirement (zero cost); if not, it searches for a layout that can be restickified to the right stick — and if that succeeds, a restickify is scheduled. 

x = torch.randn(128, 64, device="spyre")  # prior op left stick on dim 0 (rows)
x_view = x.view(128, 64)                  # free — same layout carried over
result = torch.mm(x_view, weight)         # matmul needs stick on dim 1 (K=64)
                                          # → restickify injected before mm

2
Slice along the stick dimension followed by .contiguous()
Consumer: aten.clone (generated by .contiguous())

The hardware rule

The clone / contiguous op can work on any stick layout as long as the stick expression is offset-free — i.e., the slice starts on a stick boundary. A non-zero intra-stick offset means the data must be repacked first.

Why a view causes it

When you slice along the stick dimension (e.g. t[:, 32:] on a tensor whose stick is on dim 1), the resulting view has a non-zero element offset inside a stick. Spyre can't simply start reading sticks from an arbitrary byte position inside them. The _clone_layout() function checks is_stick_expr_offset_free(): if the check fails (Case 2), it inserts a restickify before the clone to swap the stick dimension to a safe one, and the clone then acts as a second swap to restore the expected layout. 

t = torch.randn(128, 64, device="spyre", dtype=torch.float16)
# 64 elements fill exactly one stick — but slicing shifts the offset:
sliced = t[:, 32:]      # host view with intra-stick offset
c = sliced.contiguous() # triggers clone; offset detected → restickify inserted

3
Two view-derived tensors with incompatible stick layouts fed into a pointwise op
Consumer: any multi-input pointwise op (add, mul, where, …)

The hardware rule

All inputs to an element-wise pointwise op must agree on the same stick expression. The compiler picks one stick and restickifies any input that doesn't conform.

Why a view causes it

transpose() is a view — it's free. But it carries the old SpyreTensorLayout unchanged while reporting a new host shape. If you then add the transposed tensor to the original, the two tensors appear to have the same on-device tiling but now correspond to different logical dimensions. _multi_arg_pointwise_layouts() computes the set of stick expressions that are compatible across all inputs. If no single stick works for every input as-is, the optimizer (via AllSameNode) schedules restickifies on the minority inputs. 

a = torch.randn(4, 128, 64, device="spyre")  # stick on dim 2 (size 64)
b = a.transpose(1, 2)   # free view: shape (4, 64, 128), but layout unchanged
c = a + b               # a: stick on last dim (64); b: stick is now on middle dim
                        # → restickify on b (or a) to unify stick dimension

4
Dtype cast after a view that introduced an intra-stick offset
Consumer: prims.convert_element_type (dtype change, e.g. .to(torch.float32))

The hardware rule

A dtype conversion between different element sizes (e.g. float16 → float32) requires the stick expression to be offset-free. If not, the input layouts candidate returns empty, falling back to a restickify.

Why a view causes it

Float16 has 64 elements per stick; float32 has 32. A slice or view that shifts the start position within the stick dimension means the element boundaries no longer align cleanly when reinterpreting bytes for the wider dtype. In _single_arg_op_layout(), the prims.convert_element_type branch explicitly calls is_stick_expr_offset_free(); if the check fails, it returns an empty list. The caller then raises Unsupported or falls through to candidate layout scanning, which eventually results in a restickify being required before the cast can proceed. 

t = torch.randn(128, 63, device="spyre", dtype=torch.float16)
# 63 is not divisible by 64 → last stick has padding
sliced = t[:, 1:]           # shifts start by 1 → non-zero intra-stick offset
casted = sliced.to(torch.float32)  # offset + dtype change = invalid alignment
                                   # → restickify inserted before cast

5
View leaves the stick on the wrong dimension before layer norm components
Consumer: exx2 (fused mean/variance) or layernormnorm

The hardware rule

Both exx2 and layernormnorm require the input stick to be on the reduction/normalization dimension (the last logical dimension). Any other stick placement requires a restickify.

Why a view causes it

Layer norm decomposes into exx2 (mean + variance) and layernormnorm (normalize + scale). Both ops have a fixed hardware constraint: the stick must land on the last dim (the normalization dim). If a preceding transpose or reshape leaves the stick on a different dimension, the input is incompatible. _exx2_layout() and _layernormnorm_layout() both call find_stick_compatible_input_layout() asking for a layout with the stick on the reduction variable. If none of the candidate input layouts satisfy this, a restickify is scheduled via FixedInOutNode. 

x = torch.randn(batch, seq, 512, device="spyre")
# A prior transpose left the stick on dim 1 (seq), not dim 2 (512)
x_view = x.view(batch * seq, 512)   # free collapse — stick still not on last dim
y = layer_norm(x_view, [512])       # exx2 requires stick on dim 512
                                    # → restickify injected before exx2

Source

The Common Thread

A view is always free: it copies the existing SpyreTensorLayout unchanged onto the new tensor handle — no device data moves. This is done in spyre_alias_with_sizes_and_strides() in spyre_views.cpp.

A restickify becomes necessary when the next op after the view has a hardware constraint on which dimension carries the stick. Because the view changed the shape (or access pattern) without updating the device layout, there is now a mismatch between the on-device tiling and what the op expects. The compiler detects this in finalize_layouts() (insert_restickify.py) and inserts the restickify on the affected input edge.
